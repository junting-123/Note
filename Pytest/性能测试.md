# 性能测试

> 性能测试旨在评估系统在特定工作负载下的行为，以验证其是否满足速度、可拓展性和稳定性等非功能性需求。诸如”系统能同时支持多少的访问？“或”系统在超负荷运行时会发生什么？“等关键性问题。

测试网站：

黑马头条：[黑马头条-数据管理平台](https://changfenge.github.io/heima_Toutiao_global/dist/login/)

## 1、企业关注指标：



性能指标（面向客户）：

1.吞吐量：系统单位时间内处理的请求数/事务数

2.响应时间：从发出请求到收到完整响应的时间

3.并发用户数：同一时间点发起请求的虚拟用户数



资源指标：
1.CPU 使用率：服务器CPU繁忙程度

2.内存使用率：服务器内存占用情况

3.磁盘I/O：磁盘读写速率、IOPS（每秒读写次数）

4.网络I/O：网路吞吐量、带宽占用、丢包率



异常指标：
1.错误率：失败请求占总请求的比例

2.超时率：因超过等待时间而失败的请求比例



1、线程组

- 线程数（Number of Threads）：模拟的用户数量。
- Ramp-Up时间（Ramp-Up Period）：达到指定线程数所需要的时间。例如，线程数为100，Ramp-Up时间为5秒，则每秒启动20个线程。
- 循环次数（Loop Count）：测试循环的次数。



2、HTTP请求

HTTP 请求是进行性能测试的核心组件之一。无论是模拟简单的 Web 请求，还是复杂的 HTTP API 调用，HTTP 请求组件都提供了丰富的属性和参数设置选项。通过正确配置这些请求属性，测试人员可以模拟各种实际场景，确保负载测试的准确性和真实性。

HTTP请求组件的基本结构

- **服务器名称或 IP**：指定请求的目标服务器（www.example.com 或 192.168.1.1）
- **端口号**：指定目标服务器的端口号，默认 HTTP 为 80，HTTPS 为 443（80或443）
- **协议**：指定使用的协议（http:// 或 https://）。
- **方法**：指定 HTTP 请求的方法（如 GET、POST、PUT、DELETE 等）。
- **路径**：请求的资源路径，用于指定请求的目标页面或 API 路径（/login或 /api/user/details）
- **参数**：设置请求参数，用于模拟 GET 或 POST 请求中的数据提交。

### 1.1 配置线程组

总构造：

目标模拟预期或正常的用户并发数，验证系统在预期负载下是否能满足性能指标。

- 例如：10秒内模拟 100 个用户同时访问首页，检查平均响应时间是否 < 2 秒。



配置线程组（模拟100个用户）

1. 添加线程组：在“测试计划”上右键 -> 添加 -> 线程（用户） -> 线程组。
2. 配置参数 ：
   - 线程数：`100` (代表100个虚拟用户)。
   - Ramp-Up 时间（秒）：`10` (JMeter会在10秒内，把100个线程均匀地启动起来)。
   - 循环次数：勾选 永远 (这样线程就不会停止，方便我们在后续步骤中精确控制测试时长)。

![image-20260610142911421](https://cdn.jsdelivr.net/gh/junting-123/my-blog-images/img/20260610142912361.png)



### 1.2 添加 HTTP 请求

网址分析：https://changfenge.github.io/heima_Toutiao_global/dist/login/

| 字段                | 填写值                              | 说明                                               |
| :------------------ | :---------------------------------- | :------------------------------------------------- |
| **协议**            | `https`                             | 网址明确使用了 HTTPS 协议。                        |
| **服务器名称或 IP** | `changfenge.github.io`              | 这是域名部分，**不要**带 `https://` 和后面的路径。 |
| **端口号**          | (留空)                              | 使用 HTTPS 协议时，留空即默认使用 443 端口。       |
| **方法**            | `GET`                               | 访问首页通常用 GET 请求。                          |
| **路径**            | `/heima_Toutiao_global/dist/login/` | 从域名后的第一个斜杠开始完整复制。                 |

1. 右键点击 线程组 -> 添加 -> 取样器 -> HTTP请求。
2. 配置：
   - 协议：根据你的情况填 `http` 或 `https`。
   - 服务器名称或 IP：填你要测试的网站地址（例如 `www.baidu.com`），不要带 `http://`。
   - 路径：首页如果是 `/`，就填 `/`。

### 1.3 同步定时器

要做到100个用户在同一瞬间发起请求，我们需要添加一个“同步定时器” 。

1. 右键点击 HTTP请求 -> 添加 -> 定时器 -> 同步定时器（Synchronizing Timer）。
2. 配置：
   - 模拟用户组数量：`100` (意思是：我要等齐100个线程，才放它们同时去执行请求)。
   - 超时时间（毫秒）：`10000` (建议设置一个值，比如10000毫秒，防止因某些线程启动失败导致所有线程无限等待)。

### 1.5 执行测试

1. 点击绿色的 启动 按钮。
2. 等待10秒钟，测试会自动结束。
3. 查看 聚合报告，重点看这几列 ：
   - 样本：总请求数。
   - 平均值：关键指标。这里就是所有请求的平均响应时间。你需要检查这个值是否 < 2000 (因为2秒 = 2000毫秒)。
   - 错误率 %：必须是 0% 才最理想。
   - 吞吐量：系统每秒能处理的请求数。

#### 1.6.1 **聚合报告**

关键指标解读：

| 列名           | 含义                             | 如何判断达标 (你的目标)                                  |
| :------------- | :------------------------------- | :------------------------------------------------------- |
| 样本           | 发出的总请求数。                 | 应该等于 100（100个用户各1次）。                         |
| **平均值**     | 所有请求的平均响应时间（毫秒）。 | 核心指标：必须 < 2000 (即2秒)。                          |
| 中位数         | 50% 的请求响应时间小于此值。     | 通常应接近平均值。如果远小于平均值，说明有部分请求很慢。 |
| **90% 百分位** | 90% 的请求响应时间小于此值。     | 关注最慢的那10%请求的表现。                              |
| 99% 百分位     | 99% 的请求响应时间小于此值。     | 用于发现极端情况下的性能瓶颈。                           |
| 最小值/最大值  | 最快和最慢的单个请求时间。       | 观察波动范围。                                           |
| **错误率 %**   | 出错请求的百分比。               | 理想情况为 0%。大于0%就需要排查错误。                    |
| **吞吐量**     | 每秒处理的请求数。               | 反映服务器的处理能力。                                   |

#### **1.6.2 HTML Dashboard**

在命令行中进入 JMeter 的 `bin` 目录，执行以下命令：

```bash
jmeter -n -t 脚本路径/脚本名.jmx -l 结果文件路径/结果文件.jtl -e -o 报告输出目录
```

## 2、压力测试（Stress Testing）

目标：对系统施加持续增加的负载，直至其性能出现显著下降或达到资源极限，从而找到系统的性能拐点和极限负载，观察系统在过载时的行为（是崩溃、变慢还是自动熔断），也称强度测试。

- 例如：使用 JMeter 设计了在500秒内将并发用户从0平滑增至500的逐步加压场景。







## 3、稳定性测试（Soak/Endrance Testing）

目标：验证系统在长时间运行下是否存在内存泄漏、日志堆积、连接池占满等问题。

- 例如：用 500 并发持续压测 8 小时，监控内存、CPU、GC 活动。





## 4、尖峰测试（Spike Testing）

目标：模拟负载在极短时间内急剧增加的场景，验证系统的弹性伸缩能力。

- 例如：负载在 10 秒内从 100 并发突增到 2000 并发，观察系统是否超时或崩溃。
