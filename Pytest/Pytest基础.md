# 一、软测基本流程

软件测试的完整流程通常包括以下几个阶段：

- 需求评审--->需求分析（测试人员）
- 编写测试计划---->提前测试点
- 编写测试用例和评审用例---->冒烟测试
-  执行测试用例---->bug提交与管理

1.需求分析

- 熟悉产品需求说明书（PRD）
- 业务背景资料：旧产品作为参考
- 同行参考

2.编写测试计划

- 测试目的——明确工作内容、工作周期、工作风险
- 测试工作安排——人员分配，分工，硬件测试设备
- 测试范围——测试范围、优先级、测试功能
- 测试策略——测试技术与方法
- 测试开始/测试完成/上线指标——开始状态：冒烟测试通过；完成状态：测试报告发布；上线标准：Bug修复率达90%

3.编写测试用例



4.执行测试用例

- 按优先级执行

5.Bug提交与管理

软件缺陷常见类型：

- 功能问题
- 界面UI问题
- 兼容性适配问题
- 易用性问题
- 性能问题
- 安全问题

缺陷的严重程度：

- 致命：系统宕机，程序退出，核心功能不可用
- 严重：阻塞流程，主要功能不可用，数据错误，主要性能指标不达标
- 一般：不太严重的bug，次要功能不可用
- 提示：某些界面提示，例如密码规则提示
- 建议：用户体验、界面优化的建议型bug

bug的整体流程：

测试人员执行测试用例发现bug，提交bug，开发人员修复bug，测试人员回归测试，确认bug是否修复，选择关闭bug，或重新激活bug让研发继续修复

# 二、测试用例

## 2.1 设计测试用例

测试⽤例（Test Case）是为了实施测试而向被测试的系统提供的⼀组集合，这组集合包含：测试环境、操作步骤、测试数据、预期结果等要素。 

**设计测试用例的万能公式:功能测试+界⾯测试+性能测试+兼容性测试+易用性测试+安全测试**

 **功能测试**

从产品功能角度出发，验证功能是否是正确的。

- 物体：这个物体是用来干什么的
- 软件：软件实现功能

**界面测试**

- 物体：外表、材质、大小、容量
- 软件：界面、字体大小、字体颜色、页面布局

 **性能测试**

通常为一些极端的情况。

- 响应时间、吞吐量、并发数、CPU占用率
- 弱网需要借助工具来构造弱网，这里推荐荐使用 **fiddler**

  2. fiddler 进行抓包（桌面 / 移动端）

**兼容性测试**

不同版本（软件、系统），浏览器的兼容性（不同的浏览器）

- 物体：物体除了本质的功能外，是否还有其它功能
- 软件：操作系统（电脑windows、mac、linux、手机ios、Android）、设备、浏览器版本

 **易用性测试**

具备简单易上手的属性。

- 易用性：经验（操作简单、操作流程）、人性化（符合人体工学）、见名知意

**安全测试**

- 物体：物体材质是否有毒，物体是否会对人体健康造成伤害
- 软件：sql 注入、xxs 漏洞、输入有毒脚本、密码加密保存、权限控制

### 2.2.1 等价类

> ​	依据需求将输入（特殊情况下会考虑输出）划分为若干个等价类，从等价类中选出一个测试用例，如果这个测试用例测试通过，则认为所代表的等价类测试通过，这样就可以用较少的测试用例达到尽量多的功能覆盖，解决了不能穷举测试的问题。

等价类思想设计测试用例的步骤：

1. 充分理解需求
2. 划分有效等价类和无效等价类
3. 针对有效等价类和无效等价类中设计测试用例。

注意：**测试用例既要覆盖有效等价类，也要覆盖无效等价类。**

### 2.2.2 边界值

> 边界值分析法就是对输入或输出的边界值进行测试的一种黑盒测试方法。通常边界值分析法是作为对等价类划分法的补充，这种情况下，其测试用例来自等价类的边界。

边界值包含：**边界值 + 次边界值**

1. 输入框长度为 1~11，取边界值为：1、11、12、0。
2. 运动员的参赛项目为 1~3 项，取边界值为：1项、3项、0项、4项。
3. 查询面页面有 999 行，每 50 行为一页，取边界值为：输出0行、1行、50行、51行、999行。

### 2.2.5 错误推测法

> 错误猜测法是对被测试软件设计的理解，过往经验以及个人直觉，推测出软件可能存在的缺陷，从而针对性地设计测试用例的方法。

| 2    | 空格密码         | 很多系统把空格当真     | 密码是" "（三个空格）              |

| 5    | XSS脚本          | 开发直接展示了错误信息 | 账号填 `<script>alert(1)</script>` |

### 2.2.6 正交法

> 正交法的目的是为了减少用例数目。用尽量少的用例覆盖输入的两两组合。

eg.  需求：测试某网页在以下配置下能否正常运行

| 条件     | 取值个数 | 具体值               |
| :------- | :------- | :------------------- |
| 浏览器   | 3种      | Chrome、Edge、Safari |
| 操作系统 | 3种      | Windows、macOS、iOS  |
| 网络     | 2种      | WiFi、5G             |

计算：**最少测试次数 = 取值最多的条件 × 取值第二多的条件**

​			3 × 3 = 9，最少需要9种

| 格子 | 浏览器+操作系统 | 分配网络 |
| :--- | :-------------- | :------- |
| 1    | Chrome+Windows  | WiFi     |
| 2    | Chrome+macOS    | 5G       |
| 3    | Chrome+iOS      | WiFi     |
| 4    | Edge+Windows    | 5G       |
| 5    | Edge+macOS      | WiFi     |
| 6    | Edge+iOS        | WiFi     |
| 7    | Safari+Windows  | WiFi     |
| 8    | Safari+macOS    | WiFi     |
| 9    | Safari+iOS      | 5G       |

如果浏览器有4种，操作系统3种 ：4 × 3 = 12 
如果浏览器4种，操作系统4种，网络2种 4 × 4 = 16

## 四、接口测试

### 4.1 测试流程

测试用例写好后，开始执行测试，测试顺序如下：

```
第一轮：冒烟测试（5-10分钟）
   ↓ 通过
第二轮：P0级用例（核心功能）
   ↓ 通过
第三轮：P1级用例（主要功能）
   ↓ 通过
第四轮：P2级用例（边界、异常）
   ↓ 通过
第五轮：回归测试（改bug后重新测）
```

执行测试的常用工具

| 测试类型     | 常用工具                           |
| :----------- | :--------------------------------- |
| 管理测试用例 | Excel、XMind、禅道、Jira、TestLink |
| 提交bug      | 禅道、Jira、TAPD                   |
| 接口测试     | Postman、Apifox、JMeter            |
| UI自动化     | Selenium、Playwright               |
| 性能测试     | JMeter、LoadRunner                 |



接口测试是功能测试的一种执行方式，如下是接口测试的流程方法：

1. **依据接口文档**：明确需要发送什么请求（地址、参数、方法）。
2. **使用工具或代码发送请求**：
   - **工具**：如 Postman、Apifox，在图形界面里填写请求信息，点击发送，查看返回的数据。
   - **代码**：如你之前写的 pytest + requests 脚本，自动化地发送请求并断言返回结果。
3. **验证返回的数据**：检查返回的 `code`、`msg`、`data` 等字段是否符合接口文档的预期。

| 开发给的是？ | 接口文档 + 测试环境地址 + 版本号 + (可选)数据库账号      |
| ------------ | -------------------------------------------------------- |
| 怎么测？     | ①看文档 ②拼URL ③用Postman/pytest发请求 ④看返回 ⑤查数据库 |
| 测的是什么？ | 接口功能、参数校验、异常处理、返回格式、数据落库、错误码 |

接口文档就是一份“使用说明书”，告诉你怎么调用这个接口，以及它会返回什么。



### 4.2 测试接口文档（swagger规范）

        assert "body" in self.get_response().json()
    
    def test_body_not_empty(self):
        assert self.get_response().json()["body"]
```

# 二、相关词汇

测试：

1.冒烟测试：对软件的核心功能或关键业务流程进行**快速、粗略的验证**，目的是确认软件的基本环境是否正常、主要功能是否可用，从而决定是否值得投入后续的详细测试。







1.类：类就是**“蓝图”或“模板”**，用来描述一类事物的共同特征和行为。

​	类 = “生产东西的图纸”。

2.对象：用类生成的**具体事物**，带有实际的数据。

3.封装：将数据（Data） 和操作数据的方法（Method） 绑定在一起，并**隐藏内部实现细节**、**限制	外部直接访问**的一种机制。

​	封装 = 把东西装进盒子，只留一个按钮在外面给人按

4.类封装：以**类作为载体**实现封装的具体技术方案。

​	类封装 = 用“图纸（类）”来做“装盒子（封装）”这件事

5.接口：开发已经封装好的代码，只给你露了一个“呼叫入口”



url（）：网络地址
