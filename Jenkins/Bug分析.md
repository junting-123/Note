# Bug 分析

> Bug分析主要发生在**接口自动化测试**、**性能测试**以及**CI/CD流水线失败时**这三个环节

| 发现阶段       | 常见Bug类型                  | 分析方式                             | 主要工具                            |
| :------------- | :--------------------------- | :----------------------------------- | :---------------------------------- |
| 接口自动化测试 | 逻辑错误、断言错误、参数错误 | 看Allure报告的请求/响应和堆栈        | Allure + Pytest                     |
| 性能测试       | 内存泄漏、死锁、资源耗尽     | 看 JMeter 报告 + 服务器日志/容器监控 | JMeter + `docker stats` + `tail -f` |
| CI/CD流水线    | 构建/部署/脚本环境问题       | 看 Jenkins 控制台输出                | Jenkins 原生界面                    |
| 飞书通知       | 触发条件、失败率阈值         | 点进消息里的链接跳转到对应报告       | 飞书 + 各工具的 URL                 |



##  接口自动化

这一步由 **Pytest + Allure** 负责。Pytest执行用例时捕获到断言失败或异常，Allure把结果可视化。

**怎么分析：**

- **看Allure报告**：构建完成后，Jenkins会发布Allure报告（HTML格式）。重点关注：
  - **失败用例**：点进去能看到请求/响应详情、断言失败的具体字段。
  - **堆栈信息**：Python 抛出的异常，比如`AssertionError`、`KeyError`、`ConnectionError`。
  - **附件**：如果你在脚本里加了`allure.attach`，可以截图、日志、请求体等辅助信息。
- **分类Bug归属**：
  - **测试脚本bug**：断言写错了、参数化遗漏、环境配置不对 → 改脚本。
  - **业务逻辑bug**：返回的code不对、数据状态不匹配 → 报给开发。
  - **环境问题**：被测服务没起来、依赖的Mock服务挂了 → 检查容器状态。

**需要的工具：**

- Allure命令行（本地查看报告）
- Jenkins的Allure插件（自动生成并展示）



## 性能与稳定性

JMeter执行压测后，生成的报告会揭示在单次功能测试中难以发现的Bug，比如：内存泄漏、死锁、连接池耗尽、响应时间陡增等。

**怎么分析：**

- **看JMeter聚合报告**：
  - **Error% > 0**：说明有请求失败。查看`View Results Tree`监听器里的响应体，通常会有HTTP 500、Connection refused、Timeout。
  - **响应时间大幅增加**：随着并发增加，响应时间从50ms飙升到5s，说明存在性能瓶颈。
  - **吞吐量上不去**：并发增加但TPS不涨，可能是数据库连接池、CPU、内存等资源到达上限。
- **结合服务器日志分析**：
  - 压测期间，登录部署Web服务的容器或虚拟机，使用`tail -f app.log`实时观察。常见问题：数据库连接泄漏（报错`Too many connections`）、线程阻塞（日志卡住不动）、内存溢出（`OutOfMemoryError`）。
  - 可以用`docker stats`观察容器CPU/内存变化，如果内存在压测期间持续增长不回落，可能存在内存泄漏。

**需要的工具：**

- JMeter自带报告（HTML）
- 服务器日志分析命令（`tail`、`grep`）
- 容器监控：`docker stats`、`cAdvisor` + Prometheus（可选）



## CI/CD流水线失败

Jenkins流水线可能在以下阶段失败：代码拉取、镜像构建、容器启动、测试执行。这种失败不一定是业务Bug，但会阻塞流程，需要分析。

**怎么分析：**

- **看Jenkins控制台输出**：
  - 找到红色的失败步骤，展开看日志。常见问题：
  - `Docker build failed`：Dockerfile语法错误、基础镜像拉不下来。
  - `Container exited with code 137`：容器内存溢出被Kill。
  - `pytest command not found`：测试镜像里没装pytest。
  - `JMeter non-zero exit code`：性能测试脚本本身有错（比如循环变量写错）。
- **精准触发相关分析**：
  - 你提到**路径级精准触发**，即只有变更了`src/`目录才跑接口测试，变更了`jmx/`目录才跑性能测试。
  - 如果构建触发了不该跑的测试，那Bug在于你的`Jenkinsfile`里`changed`条件写错了。如果该触发的没触发，检查Git Webhook配置或者`git diff`逻辑。

**需要的工具：**

- Jenkins控制台（自带）
- Jenkins的`Pipeline Stage View`插件（可视化各阶段耗时和状态）



##  实时通知中的Bug信号

飞书机器人推送的消息本身就是Bug分析的触发器。

**怎么分析：**

- 收到 **“构建失败”** 通知：优先点进Jenkins看控制台输出，确认是脚本错还是应用错。
- 收到 **“接口测试通过率低于90%”** ：直接打开Allure报告，看哪些接口失败。
- 收到 **“性能测试95分位响应时间超过3s”** ：触发性能分析流程，调JMeter报告和服务器监控数据。
- 可以在飞书消息里直接附上关键信息，比如“接口 `/api/login` 断言失败，期望0实际1001”，这样不用点开详情就能初步判断。

**需要的工具：**

- 飞书机器人（自定义消息格式）
- Jenkins的飞书插件或`webhook`步骤
