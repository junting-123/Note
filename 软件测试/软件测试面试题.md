# 软件测试面试题

## 一、理论知识

1、B/S架构和C/S架构区别

Browser/Server（浏览器/服务器）：只需要有操作系统和浏览器就行。

Client/Server（客户端/服务器）：用户需要下载安装专门的客户端程序。



2、HTTP协议

（HyperText Transfer Protocol，超文本传输协议）是浏览器和服务器之间通信的规则，在做网络请求的时候，我们基本上是使用http协议。

常见的状态码：200成功、404找不到、500服务器错误。



3、POST与GET区别

GET获取数据、POST提交数据。



4、Cookie和Session的区别与联系

Cookie：服务器存放在你浏览器里的一小块数据

Session：服务器保存在自己内存里的用户状态信息



5、给你个网站，如何测试

1、看懂需求说明

2、做测试计划

3、写测试用例：
功能性测试：基础功能是否正常

性能测试：高并发、负载压力的时候，性能是否稳定

界面测试：页面布局是否合理，设计是否美观。

安全测试：基本的登录功能检查，是否存在溢出错误、导致系统崩溃或权限泄露

兼容性测试：看他在各个平台是否都正常运行



6、测试用例设计方法

白盒测试：逻辑覆盖、循环覆盖、基本路径覆盖

黑盒测试：边界值分析（测试边界值本身和边界值附近的值）、等价类划分（挑出代表性）、错误猜测法、场景法

 

7、软件测试阶段

单元测试：单元测试针对软件设计的最小单元——程序模块进行验证。

集成测试：各个模块组装后进行验证。

系统测试：整个系统是否正常运行。

验收测试：给客户之前进行验收。

14、什么是回归测试

当你改了代码（修bug、加功能、重构），重新运行一遍之前的测试用例，确保你的改动没有破坏原来已经能跑通的功能。

防止“回归”——也就是以前好的东西，被你改坏了。

17、持续集成测试（CI）

持续集成：持续集成（Continuous Integration，简称 CI） 是一种软件开发实践，要求开发人员频繁地（每天多次）将代码变更合并到共享的主干分支中，并且在每次合并前自动运行构建和测试，以便尽早发现集成错误。

核心目标：尽早发现并解决代码集成中的问题，确保代码始终处于可合并、可构建、可测试的健康状态。

①快反馈：代码一提交，立刻自动构建+测试，几分钟内就知道有没有问题，避免问题在后期才爆发。

②防冲突：多人并行开发，频繁合并主干，减少“集成地狱”（比如开发几周后才合并，出现大量冲突）。

③保质量：每次变更都跑自动化测试（单元测试、接口测试等），防止新代码破坏已有功能（回归缺陷）。

④可交付：确保代码随时都能被打包成一个可运行的交付件（如jar包、镜像），为后续“持续交付/部署”打好基础。



18、持续集成的优势有哪些？

持续集成的优势主要体现在效率、质量、风险三个方面：

①效率：早发现，早解决；自动化，降低重复劳动。

②质量：减少合并冲突

③风险：保持可交付状态，提升团队信心



19、 持续交付（CD）和持续部署的区别是什么？

持续交付：代码随时可以上线（但需要手动触发部署）。

持续部署：代码只要通过测试，自动就上线（无需人工干预）。



20、Git 和 SVN 的核心区别是什么？

Git 和 SVN 的核心区别在于分布式和集中式。

Git

①每个开发者的电脑上都有一个完整的版本库（包含完整历史记录）。

②大部分操作（提交、查看历史、比对）可以在离线状态下执行

③分支切换轻量且高效，鼓励频繁使用分支。

SVN

①只有中央服务器有完整的版本库，本地只有一份代码快照。

②几乎所有操作（更新、提交、查看日志）都必须连接中央服务器。

③分支本质是复制目录，速度慢且操作繁琐，通常不鼓励频繁创建。



21、Git 的工作区、暂存区、版本库分别是什么？

这三个区域是 Git 管理代码变更的核心概念，可以理解为三个不同功能的“文件夹”。

工作区：电脑上能看到的项目目录 (src/, pom.xml ）等。直接编辑修改代码的地方。

暂存区：存在于 .git/index文件中。一个临时的缓冲区域，用来暂时存放你想要提交的修改。

版本库：.git目录。Git 的核心数据库，安全地存储着项目的所有历史版本和元数据。



22、解决 Git 分支冲突的标准步骤是什么？

当两个分支修改了同一文件的同一区域，合并时就会产生冲突。手动修改冲突文件 -> git add -> git commit

解决冲突的标准步骤如下：

1、执行合并，发现冲突

```
# 假设你在 feature 分支，想把 main 分支的更新合并进来
git merge main
```

2、查看冲突文件

```
git status
```

3、手动解决冲突

打开冲突文件，会看到 Git 用特殊标记标出的冲突区域：

```
<<<<<<< HEAD
这是当前分支 (feature) 的代码
=======
这是被合并分支 (main) 的代码
>>>>>>> main
```

需要手动编辑文件，删除 `<<<<<<<`、`=======`、`>>>>>>>` 这些标记，并决定保留什么内容（可以选其中一方的代码，也可以两边都保留，甚至完全重写）。

4、标记冲突已解决

add 命令告诉 Git 冲突已经处理好了。

```
git add <冲突文件名>
```

5、完成合并

```
git commit
```



23、简述什么是Jenkins，它的主要作用是什么？

Jenkins 是一个开源的、基于 Java 开发的自动化服务器。它的核心作用是持续集成。它可以自动执行软件开发过程中的各种重复性任务。

作用：

①自动从代码仓库拉取最新代码（git）。

②自动运行编译和构建。

③自动执行测试（单元测试、接口测试）。

④自动打包、部署应用程序。

⑤自动反馈结果。



24、Jenkins 的核心组件有哪些？

核心组件：

①Master (主节点/服务器)：Jenkins 的核心进程。它负责：管理所有的任务（Job/Pipeline）、调度任务到 Agent 执行、监控 Agent 状态、提供 Web UI 界面、存储构建历史和配置信息。

②Agent / Node (代理/节点)：一个远程机器，负责具体执行 Master 分配的任务。Master 可以配置多个 Agent 来分散负载，针对不同环境（如 Windows、Linux）执行构建。

③Job / Project (任务/项目)：具体的自动化任务定义。你可以配置一个 Job 来“拉取代码 → 编译 → 测试 → 部署”。常见的 Job 类型有 Freestyle Job 和 Pipeline Job。

④Plugin (插件)：插件本质上是用来扩展 Jenkins 功能，

⑤Workspace (工作空间)：Agent 上用于执行任务的工作目录。当执行一个 Job 时，Jenkins 会从 Git 仓库拉取代码到此目录，然后在此目录下进行编译、测试等所有操作。



25、什么是 Jenkins Agent ？它的作用是什么？

Jenkins Agent (也称为 Node) 是一台独立的、被 Jenkins Master 管理的远程机器，它的唯一任务是接收并执行 Master 分配过来的构建任务。

作用：

1. 负载均衡：将多个构建任务分发到不同的 Agent 上并行执行，避免所有任务都挤在 Master 上，大大提高处理效率。
2. 异构环境构建：可以在不同操作系统或环境的 Agent 上构建、测试项目
3. 安全保障与隔离：将敏感的构建任务（如部署生产环境）放在专门的 Agent 上执行，与普通的开发测试构建隔离开，提高安全性。
4. Master 的单一职责：让 Master 专注于任务调度、状态监控、配置管理等职责，而把繁重的编译、打包、测试等实际工作交给 Agent。



26、BUG 等级

软件缺陷的等级可以用严重性和优先级来描述；

严重性：衡量缺陷对客户满意度影响的满意程度，分为
1,致命错误，可能导致本模块以及其他相关的模块异常，死机等问题；
2.严重错误，问题局限在本模块，导致模块功能失常或异常退出；
3.一般错误，模块功能部分失效；
4.建议模块，有问题提出人对测试模块的改进建议；

优先级：缺陷被修复的紧急程度；
1.立即解决（P1级）：缺陷导致系统功能几乎不能使用或者测试不能继续，需立即修复；
2.高优先级（P2级）：缺陷严重，影响测试，需优先考虑；
3.正常排队（P3级）：缺陷需要正常排队等待修复；
4.低优先级（P4级）：缺陷可以在有时间的时候被纠正；

29、手动测试和自动测试

手动测试：

1、价格成本高

2、依赖于测试人员能力，出错率高

自动化测试：

1、成本低，效率高，可以在短时间内运行更多测试

2、可以执行手工测试困难或者不可能执行的测试。比如对于大量用户的测试。



自动化测试的缺点：

1、对测试质量的依赖性极大

2、手工测试比自动化测试发现的缺陷更多

3、工具本身不具备想象力和主观能动性

31、bug 周期

```
[新建] → [已分配] → [处理中] → [已解决] → [待验证] → [已关闭]
   ↑         ↓          ↓          ↓
   |    [驳回/拒绝]   [延期]    [重新打开]
   └──────────────────────────────┘
```



bug等级：

| 级别   | 名称             | 定义                                   | 典型案例                                     | 处理要求                             |
| :----- | :--------------- | :------------------------------------- | :------------------------------------------- | :----------------------------------- |
| **S0** | 致命(Critical)   | 系统崩溃、数据丢失、核心功能完全不可用 | 启动闪退、支付失败、数据库数据被清空         | **立即修复**，阻塞发布               |
| **S1** | 严重(Major)      | 主要功能异常，影响关键业务流程         | 登录失败、购物车无法下单、消息无法发送       | **高优先级**，版本发布前必须修复     |
| **S2** | 一般(Normal)     | 次要功能异常，不影响核心使用           | 搜索排序错误、设置项保存失败、界面错位       | **正常修复**，可带病发布但有规避方案 |
| **S3** | 轻微(Minor)      | 界面显示问题、文案错误、体验不佳       | 按钮颜色不一致、提示语拼写错误、默认值不合理 | **低优先级**，可延期到后续版本       |
| **S4** | 建议(Suggestion) | 优化建议，非缺陷                       | 交互流程优化、性能提升建议                   | 产品决策是否采纳                     |

33、两个数据，判断拷贝的正确性

1. 最快：先看行数
2. 用哈希值（MD5/SHA）比对

34、请说明什么是白盒测试，有哪些主要方法。

白盒测试又称为结构测试或逻辑驱动测试，它是把测试对象看成一个透明的盒子，它允许测试人员利用程序内部的逻辑结构设计测试用例，对程序所有逻辑路径进行测试。

主要特点：

（1）测试依据是源代码，而非需求文档。

（2）目标是验证代码逻辑是否正确、路径是否覆盖完整、内部数据结构是否合法。

（3）通常在单元测试阶段由开发人员或测试人员执行。

 

主要方法：

1、 静态测试（不运行代码）

（1）代码审查：通过人工阅读方式找出潜在错误和逻辑缺陷。

（2）静态结构分析：使用工具分析代码的流程图，调用关系图，找出潜在缺陷。

（3）代码规范检查：检查代码是否符合编程规范

 

2、 动态测试（运行代码）

（1）逻辑覆盖法：

① 语句覆盖：保证程序中每条可执行语句至少被执行一次

② 判定覆盖：保证每个判断条件的“真”和“假”分支至少被执行一次

③ 条件覆盖：保证每个简单条件都取到“真”和“假”两个结果，但不一定覆盖所有判定结果

④ 条件组合覆盖：使得每个判定中所有简单条件的可能组合都至少出现一个。

 

（1）路径覆盖：

设计测试用例，使程序中所有可能的执行路径（从起点到终点）都被覆盖一次。

 

（2）基本路径测试：

在程序控制流图的基础上，通过计算环路复杂度确定程序中独立路径的数量，然后设计测试用例使每条独立路径都执行一次。



## 二、业务测试理论 

### 2.1 测试流程

1、需求评审

重点关注：

- 业务规则是否完整
- 正常流程是否闭环
- 异常场景是否说明
- 权限、状态、边界是否清楚
- 和旧功能是否有影响
- 是否存在无法测试或难以验证的点



比如订单取消需求，不能只看“用户可以取消订单”，还要问：

什么状态下可以取消

已支付能不能取消

已发货能不能取消

取消后库存是否恢复

优惠券是否退回

退款状态如何变化



2、用例设计阶段

不是凭空写：

需求文档（PRD）

原型图（静态的需求说明书，相当于前端的施工蓝图）

接口文档

数据库字段

历史bug

线上用户行为

竞品或者旧版本逻辑



3、提测后不要直接全量测试

先做冒烟测试：（核心功能是否过关）
核心页面能否打开

主流程是否跑通

关键接口是否正常

是否存在阻塞性问题

环境和数据是否可用

如果冒烟不通过，及时打回，而不是继续消耗测试时间



4、执行测试前要体现优先级

 测试是没办法穷尽完的，测试时间也不能无限拉长。最有限的时间内，找出最核心的问题。

测试核心业务流程以及高风险场景。

比如说针对电商web服务器，登录、下单、支付、权限等核心功能。

再测异常输入、功能边界条件、兼容性和易用性。



5、缺陷跟踪讲清楚闭环

Bug处理流程：

1、发现问题

2、确认是否可以复现

3、收集截图、日志、视频等信息

4、提交缺陷

5、跟踪开发修复进度

6、验证修复结果

7、做相关影响范围回归

8、关闭缺陷



5、上线前要讲测试结论

测试报告，上线前的决策依据

上线前要说明：

- 测试范围；

### 2.2 测试用例设计方法如何结合真实业务

1、理解业务，再选择方法

不同业务适合不同方法：

- 输入框、金额数量适合等价值和边界值
- 多条件组合适合判定表
- 复杂逻辑适合场景法
- 状态变化适合状态迁移法
- 历史问题集中区域适合错误推断法

如果不理解业务，上来套模板，用例容易变成形式主义



2、等价类要结合有效或无效业务数据

以手机号注册为例，可以分为：

- 有效手机号；
- 少于11位；
- 多于11位；
- 非数字字符；
- 未注册手机号；
- 已经注册手机号；
- 被禁用手机号；
- 境外手机号是否指出



3、边界值要关注业务边界

边界值不只最小值、最大值。

比如优惠券规则是“满100减20”，测试点：

- 订单金额99.99
- 订单金额100
- 订单金额101.01
- 多件商品满100
- 使用积分后满100
- 运费是否记入满减门槛

真正容易出问题的边界，往往是业务计算边界。



4、判定表适合多条件组合

比如审判功能是否允许提交，可能受多个条件影响：

- 用户角色；
- 单据状态；
- 审批金额；
- 是否超过预算；
- 是否已被别人处理



先列条件，再列动作：

- 普通员工+草稿状态+金额正常：允许提交
- 普通员工+已提交状态：不允许重复提交
- 审批人+待审批状态：允许审批；
- 非审批人+待审批状态：不允许审判
- 审批人+已撤回状态：不允许审批



5、场景法

业务系统最重要的是流程。

以下单流程为例，主流程是：

1. 选择商品；
2. 加入购物车；
3. 提交订单；
4. 使用优惠券；
5. 支付成功；
6. 生成订单；
7. 扣减库存。

异常流程包括：

1. 商品下架；
2. 库存不足；
3. 地址为空；
4. 优惠券过期；
5. 支付失败；
6. 重复提交；
7. 支付成功但订单状态未更新。



6、状态迁移法适合订单、审批、工单类业务

有些业务的核心不是输入，而是状态变化。

比如订单可能包括：

- 待支付
- 已支付
- 已取消
- 已发货
- 已完成
- 退款中
- 已退款

测试时要关注：

- 哪些状态可以流转；
- 哪些状态不能逆向流转；
- 重复操作是否被拦截；
- 状态变更后相关数据是否同步；
- 前端展示、接口返回、数据库状态是否一致



七、错误推测法来自经验积累

根据历史问题判断风险：
常见高风险点包括：

- 重复点击导致重复提交；
- 网络超时导致状态不一致；
- 权限校验只做前端不做后端；
- 金额精度计算错误；
- 缓存未刷新导致数据旧；
- 多人同时操作导致并发问题。



> 我设计测试用例时不会只套方法，而是先分析业务流程和风险点。对于输入类字段，我会用等价类和边界值；对于多条件判断，比如权限和审批规则，我会用判定表；对于下单、支付、审批这类流程，会用场景法覆盖主流程和异常流程；对于订单状态、工单状态，会用状态迁移法；最后结合历史 Bug 做错误推测，补充重复提交、权限绕过、数据一致性等高风险场景。



### 2.3 登录功能

1、说明登录的测试目标

- 合法用户能正常登录；
- 非法用户不能登录；
- 登录态能正常生成、保持和失效；
- 权限和安全控制有效；
- 异常场景下系统提示合理；
- 接口、数据库、日志数据一致。
